# 开发日志

## 项目起点

项目最初用于赛马娘同人小说和角色扮演提示词的资料收集。早期由专门的 agent 工作流组织查询与写作，后来把查询能力整理成 Wiki Skill，供能读取项目、执行命令的 AI 助手使用。小说与角色提示词最初都是查询资料后配合任务提示生成的；现在分别有专用写作 Skill，负责资料核对、创作和输出整理，继续复用 Wiki 查询。

抓取也试过几条路：用 Crawl4AI 访问页面，把网页转成 PDF，再尝试用 MarkItDown、Qwen2.5-VL 转成 Markdown。效果没有达到预期，之后改为优先使用站点开放的 MediaWiki API；对不适用的站点读取公开 HTML 或 JSON。视觉抓取代码保留供特定页面使用，当前角色资料查询走 HTTP 正文和数据接口。

## 2026-10-13

### 先把正文拿完整

检查三个 Wiki 的输出时，发现“请求成功”和“资料完整”差得很远。旧测试只检查有没有文字，角色档案、技能表和整段台词丢了也能通过。

Bwiki 的问题最明显。东海帝皇页面中的语音由普通模板生成，旧代码只展开 `{{:页面}}` 这种嵌入页引用，拿到的是角色 ID 等参数。增加递归深度没用。改用 MediaWiki 的 `action=parse` 后，站点先展开模板，再从返回的 HTML 提取正文。这个样本里的 226 条日文语音和 226 条简中语音都保留下来了。

三个站最后采用了不同的取法：

| 站点 | 原来的问题 | 现在的处理 |
| --- | --- | --- |
| Bwiki | 源码里的模板没有展开，档案和台词缺失 | 通过 `action=parse` 取渲染 HTML |
| 萌娘百科 | `extracts` 丢掉大量表格；`parse` 和 `revisions` 返回权限错误 | 读取公开页面，从正文模板中取出 HTML 后重新解析 |
| umamusu.wiki | 清洗源码后仍有多行模板残留 | 同样改用 `action=parse`，保留档案表和正文链接 |

萌娘还有一个解析细节：正文放在 `template#MOE_SKIN_TEMPLATE_BODYCONTENT` 里，直接调用 BeautifulSoup 的 `get_text()` 会漏掉其中的文字。需要把这段 HTML 单独解析一次。

正文处理现在由 CLI、MCP 和 skill 共用。关联子页保留链接，获取人物主页不会顺带下载所有关联页面。检查内容时也不能只比字符数，合并单元格展开、双语台词和 Markdown 链接都会让输出变长。

顺便合并了重复的 opener 和浏览器 UA 定义。这里修了一个代理问题：原来有的入口即使传了 `use_proxy=False`，仍可能从系统设置读到代理。现在明确禁用代理时，会同时忽略项目配置、环境变量和系统代理；API 请求继续使用项目自己的 UA。

### 补充日文资料和资源索引

接着看了 wikiru 和 Umapyoi。两者都能补资料，不过用途不同。

wikiru 使用 PukiWiki，角色档案和折叠台词已经在普通 HTML 里，不需要浏览器执行脚本。接入时保留了“条件、台词、备注”的表格关系和脚注，去掉评论区。这里用了 `lxml`：同一份页面交给 `html.parser`，部分台词会落到正文容器外。页面名也要保留 `/?日文标题` 的形式，不能套用 MediaWiki 的 URL 规则。目前搜索只覆盖角色索引。

Umapyoi 提供 JSON API，适合补角色档案、衣装、支援卡和图片索引。对接时用 `game_id`，不能用数据库里的 `id`；例如东海帝王的 `game_id` 是 `1003`。空字段照原样保留，资源链接也不能默认可用：抽样时就遇到了旧图片地址返回 404。团体支援卡的主角色 ID 可能是其他成员，因此没有按这个字段直接过滤。

Google 函数继续保留，但 MCP 不导入、不注册，skill 也不调用。角色资料的主流程不依赖 Google。

### Bwiki 左下角的小人

丸善斯基页面左下角的小人实际上是两张透明 PNG。页面脚本每点击五次切换一张，转身效果由 CSS 完成。文件末尾的 `0010`、`0011` 是两个互动状态，不能标成正面和背面。

换装也有对应图片，麻烦的是游戏衣装 ID 和图片资源 ID 不一定相同：

| 丸善斯基衣装 | 游戏衣装 ID | 图片资源衣装 ID |
| --- | --- | --- |
| 原皮 | `100401` | `100401` |
| 夏日换装 | `100402` | `100430` |
| 正月换装 | `100403` | `100410` |

所以下载器读取页面 Qchar 区域实际引用的文件，再用 `imageinfo` 查询原图地址，不按衣装编号猜地址。保存时按角色和游戏衣装分目录，文件名保留资源 ID，两者的对应关系写入下载记录。

新增的 `biligame-chibi` 任务默认保存到 `results/biligame_chibi`。每张图校验通过后才写入文件，并保存进度；再次运行会检查本地哈希，跳过完整衣装、补齐缺失或损坏的图片。角色索引的读取代码移到 `character_targets.py`，与原来的资源下载流程共用。

### HTTP 567 的排查

开始以为是请求过快，把小人下载的默认请求间隔从 2 秒加到了 5 秒，衣装页间隔从 5 秒加到了 10 秒。但等了六分钟再试，东海帝皇的一套换装仍然返回 567；后来特别周的第一条请求也失败了。单纯加等待时间没有解决这次问题。

进一步检查发现，失败响应带有 `Server: TencentEdgeOne` 和 `EO-LOG-UUID`，正文是拦截页。[腾讯云文档](https://cloud.tencent.com/document/product/1552/101095)将这种 567 归为自定义规则、限频或 Bot 管理规则拦截。浏览器访问同一个 API 地址却能拿到 JSON，不能据此认定整个 IP 都被封了。

原请求已有项目 UA，但缺少 `Accept` 和 `Referer`。补上 `Accept: application/json` 和同 Wiki 的 `Referer` 后，同一请求返回了 200，特别周原皮和此前失败的东海帝皇换装都完成了下载。这次没有用 Cookie，也没有更换 UA。具体命中了哪条规则、两个请求头各起了什么作用，没有做进一步拆分试验。

现在报错会留下处理阶段、状态码和 EdgeOne 请求编号，方便下次排查。遇到 403、429、567 会停止并保留进度。`curl_cffi` 暂时没有引入，继续使用现有的 `urllib` 请求层。

全量下载已按请求间隔 10 秒、衣装页间隔 20 秒开始运行，尚未统计最终结果。限速只在同一进程内共享，不同时启动多个下载任务。
